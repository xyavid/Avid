# 架构推导判据

用于出图、改模块边界、评审设计时的判断依据。

每条以**检查点**给出：能满足即通过，不能满足则该设计结论不成立；未覆盖的检查点显式标注为「未验证假设」。章节顺序即分析顺序。

只分析与当前问题真正相关的检查点，不为凑齐条目而制造复杂度。使用约束见 `AGENTS.md` 第 5 节。

## 1. 变化优先

先定位变化，再谈结构。

- 列出未来最可能变化的东西：业务规则、数据结构、UI、外部 API、数据库、算法、执行策略、权限、配置、部署方式、性能 / 可靠性要求。
- 给每处变化标注频率、时间窗与代价；高频、高风险、昂贵的排在设计优先级最前。
- 追问：这一变化迫使哪些模块跟着改？哪些本不该跟着改却被绑上了？
- 找「总因同一原因一起改」的一组模块，判断它们背后是否漏掉了一个尚未命名的概念或边界。

## 2. 具体先行

从最简单、可运行、具体的实现开始，抽象只作为回应。

- 引入每层抽象前回答：它解决的是已经发生的问题，还是预测中的问题？
- 抽象准入证据要三项取其一并指名：真实重复、真实变化、真实耦合。
- **删除测试**：删掉这个抽象后若代码更简单且没有边界丢失，就撤回；若多个变化重新耦合、状态边界消失或替换变难，则保留并说明它守住了什么。
- 比较**总复杂度**（含跨模块依赖、数据同步、测试、失败传播），而非类数或代码行数；允许局部更复杂以换取系统更简单。

## 3. 耦合

结论性语言（「职责不同」「松 / 紧耦合」）不作为分析结果。

- 对每条 A→B 依赖逐项回答：A 用了 B 的什么？B 变时 A 是否必须变？A 变时 B 是否必须变？A 是否知道 B 的内部细节？
- 逐维度拆开并指名**耦合机制**：结构、数据、控制、时间、生命周期、部署、运行时、组织（ownership）。
- 检查共享可变状态、隐式调用、全局单例、共享数据库表、共享配置、强制同步发布的版本号。
- 指出**复杂度传播路径**：一个变化从哪开始、经过哪些模块、跨多少进程 / 数据库 / 团队；路径长度超过一次本地修改即为架构信号。

## 4. 边界与决定权

每个边界都要能回答「它隔离了什么」和「谁说了算」。

- 逐项指派**所有权**：谁决定、谁执行、谁拥有状态、谁拥有数据、谁负责失败 / 重试 / 恢复 / 权限 / 生命周期。
- 检查业务策略是否与执行机制、持久化、基础设施细节混在一处；混则评估拆分。
- **高价值边界**优先投入：隔离高频变化、高风险、昂贵变化、不同生命周期、不同 ownership、不同可靠性 / 安全等级、不同扩展方式的地方。
- 拆分粒度检查：若若干模块总是同时修改、同时部署、共享大量状态、互相调用，则判定为「物理分开、逻辑未分」，合并或重划；若单个模块内出现互不相关的大量变化、多个生命周期或多个 ownership，则拆分。
- 检查依赖方向：高层策略是否反向依赖了数据库、HTTP、SDK、框架 API 的具体细节。

## 5. 数据所有权与状态生命周期

服务边界多数其实是数据所有权问题。

- 对每份数据回答：谁创建、谁拥有、谁可改、谁可读、谁是 Source of Truth、复制后谁负责同步。
- 对每个 state 回答：谁创建 / 读 / 改 / 删、何时持久化、能否恢复、并发修改如何处理、版本与过期如何管理、如何迁移。
- 按类型分别处理：无状态、临时、会话、持久、派生、缓存、分布式；派生与缓存须指明其权威来源。
- 建模**业务生命周期**，并区分对象、请求、会话、任务、工作流、进程、服务、数据库各自的出生—活跃—暂停—恢复—终止，以及终止后能否恢复。

## 6. 不变量

先定义不可破坏的性质，再指派唯一的守护者。

- 列出系统 / 模块中「永远不能被破坏」的性质（余额非负、不重复扣款、消息不丢、不越权访问、状态不倒退、操作幂等，按业务具体化）。
- 为每个不变量指派**负责保证它的那一层**，并检查是否存在多条路径可绕过它。
- 检查所有写入路径是否都经过该守护层，包含批处理、后台任务、运维脚本与人工修数。

## 7. 失败与恢复

失败路径与正常路径同等级设计。

- 每个模块回答：它怎么失败、失败影响谁、失败后谁知道、谁负责重试、重试是否安全、何时停止重试、能否恢复、是否产生重复操作、是否需要补偿或人工介入。
- 按类型分别定策：临时失败、永久失败、业务拒绝、权限拒绝、数据错误、环境错误、依赖错误、程序错误。
- 覆盖路径：失败、恢复、超时、部分失败、重复、降级——逐条给出对应机制。
- 任何异步化（queue / event / worker / stream / background job）须先回答：为什么不能同步、解决哪一种约束、消费者能否延迟、能否重复、是否要求顺序、消息是否要持久化、积压 / 宕机 / 重复消费如何处理。

## 8. 并发与一致性

并发在设计期显式建模，不留给事后 bug。

- 指出谁与谁可能同时操作、共享什么、是否允许竞态、谁提供互斥。
- 逐项选择并说明理由：乐观锁、悲观锁、version、队列串行化、幂等键、允许最终一致。
- 一致性按坐标声明：**哪一种数据、在哪个时间窗口内、对谁一致**；区分必须强一致与允许最终一致的部分，指明谁负责修复不一致，以及用户看到中间状态时的表现。

## 9. 依赖与不可靠边界

- 列出全部外部依赖：数据库、云服务、第三方 API、SDK、框架、文件系统、队列、支付 / 模型供应商。
- 对每个依赖回答：谁依赖它、它变时谁受影响、它不可用时怎么办、如何测试、如何替换、协议由谁定义。
- 检查外部概念是否渗入核心业务模型；若是，在核心与外部之间放置适配边界。
- 对每个 A→B 远程调用，按「请求 / 响应可能丢失、可能重复、可能延迟、连接可能中断、服务可能重启、两端可能短暂看到不同状态」建模，并给出对应的超时、幂等、重试与对账方案。

## 10. 边界代价与权衡

边界不是免费的，先算代价再决定。

- 每个待建边界列出其成本：序列化、延迟、失败面、运维与部署复杂度、调试难度、一致性问题、团队协作开销。
- 回答：这个边界带来的隔离价值是否覆盖上述代价？
- 方案比较给至少两个选项，逐项对比复杂度、成本、可靠性、延迟、一致性、可运维性、安全、演进性、ownership、迁移难度。
- **反事实测试**：需求全变、规模 ×100、依赖长期不可靠、数据库更换、多区域、实时或离线、团队从 1 变 10 时，哪些边界仍然成立、哪些会崩。
- 每个结论写明：解决了什么、牺牲了什么、增加了什么复杂度、在什么条件下成立、什么条件下失效、出现什么信号时重新考虑。

## 11. 可逆性与决策强度

按撤销难度分配论证成本。

- 给每个决策标注可逆性等级：易撤销（命名、函数）、中等（模块边界、数据库选型）、难撤销（数据模型、公开 API）、极难撤销（分布式数据所有权、跨团队协议）。
- 难撤销者要求更强证据与更完整的失败 / 迁移方案；易撤销者允许直接选定并在实现中调整。
- 检查本次决策将来如何撤销：迁移路径、双写 / 双读、回滚点、旧版本兼容范围。

## 12. 运行与演进

- 性能从工作负载推导：请求量与数据量、延迟目标、吞吐、尾延迟、读写比、峰值形态，然后才讨论 cache、index、batch、并行、队列、分片、复制、反规范化、预计算。
- 规模必须指名扩展对象：用户、请求量、数据量、区域、功能数量、开发并发、团队数量；不同维度导向不同架构。
- 安全按信任边界处理：身份认证、授权、数据隔离、secret、输入验证、审计、最小权限、供应链、运行环境；逐条回答「谁信任谁」「哪一步握有执行真实世界动作的权力」。
- 可观测性随边界布置：每个重要边界回答出问题怎么看、请求走到哪、哪一步失败、如何区分业务失败与基础设施失败、如何串联一次完整执行（logs / metrics / traces / events / audit）。
- 部署与版本同属架构：什么一起部署、什么独立部署、什么必须一起回滚、migration 与向后兼容、新旧版本共存与数据 / 事件 / API 兼容性、如何迁移与回滚；组件无法独立演进时，指出绑定它的部署耦合。
- 每个架构写明适用条件与失效信号：在什么情况下成立、什么时候不成立、出现什么信号后重新评估，以及下一次变化最可能落在哪里（新增功能、替换实现、扩容量、拆 / 合模块、迁数据、改协议分别是否容易）。
