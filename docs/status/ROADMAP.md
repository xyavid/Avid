# Avid 路线图

本文件写**未来方向**：下一个版本做什么、之后有哪些候选、每条的触发条件与解禁条件。
它**不含已完成阶段的账本**——那份账本在 `dev/plan/roadmap.md`（本地过程文档，不入库，
记录每个阶段的「目标 / 实现方式 / 产出结果」）。

| 想知道 | 去哪 |
|---|---|
| 已完成阶段逐个做了什么 | `dev/plan/roadmap.md`（本地，不入库） |
| 现在是什么、能什么、不能什么 | `docs/status/CURRENT_STATE.md` |
| 已具备的能力与入口 | `docs/status/CAPABILITIES.md` |
| 数字现状（有哪些、缺哪些） | `docs/status/BENCHMARK.md` |
| 架构与门禁 | `docs/status/ARCHITECTURE.md` |

## 0. 排期规则

1. **划分、优先级与顺序都在对话中确定，不预先排期。** 本文件列的是**候选与触发条件**，
   不是待办清单；候选不构成承诺。
2. **一个阶段一件事**：动工前先澄清需求、出图（文件清单 / 目录树 / 架构图），再动工；
   收尾按商定的验收标准逐条给证据。
3. **每完成一个阶段，至少回写 `CURRENT_STATE.md` 的九问与 `CAPABILITIES.md` 的对应条目**；
   涉及数字的（性能/效果）同时回写 `BENCHMARK.md`；涉及分层或依赖的更新 `ARCHITECTURE.md`；
   完成的阶段本身记进 `dev/plan/roadmap.md`，**不往本文件追加**。
4. 候选的**排序依据只有两条**：触发条件是否已经出现、它是否解除 `CURRENT_STATE.md` 里
   被点名的最差能力或最大瓶颈。没有触发条件的候选不因为「看起来该做」而升级。

## 1. V1（评测集与首个基线）：已交付 4/5，剩一条对照

**目标**：把参考场景 R（读取本地文件 + 计算）变成可执行的评测集与首个可对比基线，
并让它成为改动前后的常规门禁。

**现状（commit `1ece312`）**：仪器已建成在 `benchmarks/`（AvidBench v0.1，12 条只读 case ×
3 个变体 + 五种确定性判定器 + 轨迹落盘），首个基线已落盘（`BENCHMARK.md` §9）。它与本节的
关系是「超集」：R 类只读任务对应 `basic` + `long_horizon` 两类共 7 条，另外 5 条按机制分了类，
但**交付物形态换了地方**——不是 `evals/`，是 `benchmarks/`（理由与偏离见 `BENCHMARK.md` §7）。

**为什么是它**——三个理由指向同一件事（详细论证见 `CURRENT_STATE.md` §6、§7）：

1. `dev/plan/roadmap.md` 把它列为**唯一**「已明确的必经项」，需求把它定为分水岭（决策 D-05）；
2. 它同时是「最差能力（评测与度量）」与「最大技术瓶颈（无可度量反馈闭环）」的解药；
3. 它把项目级成功标准第 3 条「改动前后有可对比的评测数字」从声明变成机制。

**交付物**（详细协议见 `BENCHMARK.md` §7，逐条现状见该文「本轮落地对照」）：

| # | 验收标准 | 判定方式 | 现状 |
|---|---|---|---|
| 1 | 任务集存在且客观可判 | 只读、每条带期望结果与判定方式 | ✅ `benchmarks/cases/v0/` 12 条 + 69 个 fixture 文件；全部只读、无 LLM judge |
| 2 | 一条命令出通过率与失败分类 | `uv run pytest -m eval -q`（或 `python -m benchmarks.run`） | ✅ 两个 marker 默认不跑；失败分类为能力 / 预算 / 模型 / 权限 / 基础设施 / 取消 |
| 3 | 首个基线落盘且可追溯 | 数字写进 `BENCHMARK.md`，含 commit、模型、机器、日期、上限 | ✅ `BENCHMARK.md` §9 |
| 4 | 能给出前后对比 | 同一任务集跑一次「改 prompt 或压缩阈值」的对照，产出两组数字与差值 | ❌ **未做**：机制在（同一任务集 × 多臂/多 commit 都落盘、差值可算），但没跑过一次单变量对照 |
| 5 | 不拖慢日常门禁 | 默认 `pytest` 不含评测；提交前可一键跑；不进 CI 全量 | ✅ `addopts` 排除 `eval` / `eval_smoke` |

**下一个版本只解决第 4 条，还是先解决别的——在对话中定。** 首轮基线给出的信号是**任务集偏易**
（11 条非会话 case 上三个变体全部通过，成功率没有区分度；`compactions` 36 次运行里一次都没触发），
所以下一步的候选至少有三个，且互斥：① 加难度分层（L3–L5：多失败点、长上下文、深依赖）后再比
变体；② 先跑一次 prompt / 压缩阈值的单变量对照，把第 4 条兑现；③ 先冻结阈值（含
`web/budget.json` 的 `frozen_at`）。本文件不预先排期。

**V1 曾明确不做（仍然不做）**：长期记忆、沙箱、多 provider、SQLite 后端、压缩条目、任务图下一段、
前端 a11y 与视觉回归、虚拟列表。**理由**：V1 的验收标准全都不需要它们；一旦并行开工，
「只解决一个问题」就失效。

**原本「动工前必须先定」的那件事已经定了**：评测用**真模型 + 固定模型版本**（`AVID_MODEL`，写进
结果文件），录制回放**只留给以后的机制回归**，本阶段没有建回放层——数字全部依赖真模型，因此
不进 CI 全量。这条取舍的代价写在这里：同一个 case 重跑会有抖动，所以数字只能与「同模型、同机器、
同 limits」的运行相比。

## 2. 候选池（不排期，按触发条件组织）

每条给：现状（写清为什么现在不做）、**触发条件 / 重新考虑信号**（尽量抄自设计文档原文，
以便有一天信号出现时能直接判定）、以及它触及哪份现状结论。候选分六组。

### A. 内核与可靠性

| 候选 | 现状与代价 | 触发条件 / 信号 |
|---|---|---|
| hook 执行超时 | **没有超时机制**：`src/avid/runtime/hooks.py` 零 `timeout` 命中，挂住的回调会永久挂住整个运行；失败关闭只覆盖「抛异常」 | 出现一次真实挂起，或 hook 从「进程内纯函数」变成可能访问网络/外部进程 |
| hook 失败模型细化 | 现在只有「抛异常 = 阻断」一种；没有重试、没有隔离超时、没有「只记日志不阻断」的声明式选项 | 出现第二种「希望它失败但不阻断」的 hook 语义需求 |
| 并行工具执行 | 现在是 `execute_batch` 串行执行（协议上合法，subagent 才并行） | 出现「一轮里多个独立工具调用，串行明显拖慢」的实测（`runtime-architecture.md:465` 把「并行工具执行」列为下一处最可能的变化之一） |
| provider 替换 / 多 provider | 只有一条 OpenAI 兼容路径，无抽象；需求 D-03 明确早期不做多 provider 抽象 | 必须接第二个端点或换协议（`runtime-architecture.md:465` 列为 ④） |

### B. 会话、成本与记忆

| 候选 | 现状与代价 | 触发条件 / 信号 |
|---|---|---|
| 压缩条目 | 未做；长会话续接要重新压缩一次 | **长会话续接需要重复压缩时**（`runtime-architecture.md:635-642`） |
| usage / token 台账 | 未做；token 只在运行内累加、**不落盘**，无成本统计（`src/avid/session/types.py:149` 自述该取舍） | **要统计 token 成本时**（同上） |
| operation 状态机 | 未做；取消只在两个检查点生效，进程崩溃后无法恢复运行 | **要在途任务跨进程恢复时**（同上） |
| SQLite 后端 | 未做；JSONL 是「整文件解析 + 尾部窗口」，量级门禁把 200 会话 / 5000 条钉在 1.5s / 3s | **会话数量让 JSONL 重放变慢时**（同上；量级门禁只是「不许退化」的下限，不是容量设计） |
| 长期记忆 | 未做；跨会话只有条目树与任务图，没有提炼 / 召回 / 遗忘 | 出现「同一个事实反复讲给 agent」的真实使用证据；或参考场景扩到需要跨会话知识 |
| 会话 id 带工作区（加索引） | 现状是「按会话操作要扫各工作区的 `repo.list()`」，代价与「工作区数 × 会话数」成正比 | **工作区或会话数量上去后定位明显变慢** → 把工作区 id 放进会话 id 或加一层索引（`workspace-permission.md` §8） |

### C. 任务图与多 agent

| 候选 | 现状与代价 | 触发条件 / 信号 |
|---|---|---|
| 子 agent 的 `owner` 身份 | 未做；`owner` 只是一个字符串，无法区分是哪个 subagent 认领的 | **需要区分「哪个 subagent 认领的」时**——把 actor id 放进 `RunState` 并让工具外壳读它（`runtime-architecture.md:1201-1210`①） |
| 任务工具进审批闸门 | 未做；六个任务工具不在 `APPROVAL_RULES` 里 | **出现任务文件被写成不该写的内容时**——在 `APPROVAL_RULES` 加一行（同上②） |
| 跨进程互斥（任务） | 未做；任务库锁是按目录的进程内 `RLock` | **多进程同时操作同一工作区时** → 改文件锁（同上③） |
| `completed` 回退 / `in_progress` 释放 | 未做；状态机只有 `claim`/`complete` 两条边，没有回退动作 | 需要回退时**必须在状态机上新增动作，而不是直接改 `status`**（同上④） |
| 给人看的任务列表 | 未做；Web 任务板只读，CLI 无 `--list-tasks` | 出现「想手工看一眼任务图」的需求（同上⑤） |
| subagent 子事件转发 | 未做；子运行不向父事件流发事件，父运行里只表现为一段文本 | 需要在界面上观察子 agent 进度或失败原因时（`frontend-architecture.md` D10） |

### D. 前端与体验

| 候选 | 现状与代价 | 触发条件 / 信号 |
|---|---|---|
| 性能门禁与基线（C1–C5、C10、C12） | **没有脚本**：`web/scripts/` 只有 5 个门禁/构建脚本，无 `perf:*`，无计时断言；`web/budget.json` 的 `frozen_at` 仍是 `null` | 设计文档 §9 的测量协议已给，**阈值待第一次测量前冻结**；`frontend-architecture.md:988` 第 1 条自认「全部性能目标值未做任何实测」 |
| 虚拟列表 | 未做 | **注入 1000 条后 p95 帧 > 33ms**（`frontend-architecture.md:977-982`） |
| a11y 与视觉回归用例 | 约定有、用例零：`playwright.config.ts` 写了截图约定，但 spec 里零截图断言、零 axe 断言 | 视觉回归在无头环境稳定后（字体加载时序与亚像素噪声是已知风险） |
| delta 对续接的影响 | 未验证：进程在流式过程中被杀时，用户看到的是「等待中」而不是半截文本 | 这个体验被判定不可接受时（`frontend-architecture.md:988` 第 9 条） |
| 第二个前端表面（桌面壳 / IDE 面板） | 未做 | 出现第二个表面 → 升级为独立 IDL（同上失效信号） |

### E. 安全、权限与部署

| 候选 | 现状与代价 | 触发条件 / 信号 |
|---|---|---|
| 危险/越界的结构化字段 | 警告只在 `reason` 文本里，没有结构化 `warning` / `target` | **审批卡片要按风险分色或按目标分组时**（`workspace-permission.md` §5.3 / §8） |
| 按会话或按分支区分权限 | 未做；权限模式存在工作区注册表里，是工作区级默认 | 需要按会话或按分支给不同模式时（同上） |
| 真沙箱或命令白名单 | 现状是**护栏不是沙箱**：权限判定是命令行文本正则（15 条 / 14 类），可被间接调用绕过；`bash` 以本进程权限运行 | 出现「以为被拦、实际没拦」的真实事故，或评测/真实使用中抓到一个造成不可逆损失却未被问的命令（同上） |
| 鉴权与远程访问 | 不打算做；当前只有回环监听 + Host/Origin 白名单，**没有认证** | 出现第二个真实使用者或远程使用需求 → 需要一轮独立设计（鉴权、工作区隔离、CSRF、审计） |
| 持久授权（跨运行记住「同意一次」） | 未做；账本只活一次运行 | 每次运行都要重复点同一路径/命令、明显碍事时（同上 §8 第一行） |

### F. 分发与工程

| 候选 | 现状与代价 | 触发条件 / 信号 |
|---|---|---|
| 前端门禁脚本接入 perf / e2e CI | e2e **不进 CI**（需要真实模型与起着的内核）；无 pre-commit / Makefile / justfile；无覆盖率 | 出现「本地不跑就漏」的回归，或 V1 的评测集需要一条统一入口时 |
| 事件类型升级到契约生成 | 现在是「Python 单点 + 前端联合类型比对」的机械检查 | **事件类型超过 25 个**（现 18 个）（`frontend-architecture.md:977-982`） |
| 文档漂移清理 | 四处已知漂移见 `ARCHITECTURE.md` §8（前端设计文档状态行、durable 示例表漏项、CI 注释、runtime §16.6 未做清单） | 任一文档再次被当作事实引用而引错时 |

## 3. 明确的非目标与解禁条件

非目标是「当前主动不做」，**不是永久禁令**；条件满足即启动，不需要重新论证
（`dev/drafts/requirements.md:39-74`，本地记录）。逐条状态按事实核对：

| 非目标 | 状态 | 解禁条件 | 条件是否已满足 |
|---|---|---|---|
| 训练 / 微调模型 | 架构外，基本不做 | 编排层与上下文策略均已优化到位、且被证明是瓶颈时重新评估 | 否（无评测基线，「被证明是瓶颈」无从谈起） |
| 多用户 SaaS 后端 | 暂缓 | 单人版稳定运行，**且出现第二个真实使用者** | 否（唯一使用者是作者） |
| agent 自我修改自身代码 | 暂缓 | **评测基线与权限模型均已建成**，且改动一律走人工审批 | **权限模型已建成、评测基线未建成 → 仍暂缓**（这正是 V1 要解除的条件之一） |
| 追求工具数量 / 铺开工具生态 | 暂缓 | 参考场景 R 通过后按真实需要增量生长，不做预埋 | 否（R 尚未量化执行） |
| 与商业产品功能对齐 | 不做对标 | 有具体价值的需求出现时按需求做，永不按竞品做 | — |
| 插件生态、协议互操作（MCP 等） | 暂缓 | 出现「必须接某个外部系统」的真实需求 | 否 |
| 真正的沙箱隔离 | 暂缓（现为护栏） | 见 §2-E：出现「以为被拦实际没拦」的事故 | 否 |

## 4. 什么时候重估路线

信号出现即重估**本文件的排序**（信号原文来自各设计文档的失效条件）：

| 信号 | 说明什么 | 影响哪些候选 |
|---|---|---|
| 评测集跑通后通过率长期很低、且失败集中在「预算不足」 | 瓶颈在上下文与轮数，不在 prompt | 提升 B 组（压缩条目、上下文策略）的优先级 |
| 失败集中在「工具错误」 | 工具描述与参数设计是瓶颈 | 提升 A 组（工具协议）优先级 |
| 缓冲淘汰频繁触发 `resync` | 重放缓冲太小或消费太慢 | D 组（传输与前端） |
| 同时运行会话 > 5 或同源连接数成为瓶颈 | 传输形态到了上限 | D 组（传输升格） |
| 注入 1000 条后 p95 帧 > 33ms | 渲染到了上限 | D 组（虚拟列表） |
| 工作区或会话数量上去后按会话定位明显变慢 | 索引缺失 | B 组（会话 id 带工作区 / 加索引） |
| 单会话长度让 JSONL 重放变慢 | 存储后端到了上限 | B 组（SQLite 后端） |
| 事件类型超过 25 个 | 人工同步契约不再划算 | F 组（契约生成） |
| 出现第二个真实使用者 / 远程使用 | 单用户本地前提失效 | E 组（鉴权、隔离）——需要一轮独立设计 |
| 出现「以为被拦实际没拦」的事故 | 护栏不足 | E 组（沙箱 / 白名单） |

## 5. 与其他四份文档的联动

```
CURRENT_STATE.md（最差能力 / 最大瓶颈 / 最大未知）
        │  指出该往哪走
        ▼
   ROADMAP.md（V1 与候选池）──► 动工前澄清 + 出图（AGENTS.md §3）
        │                              │
        │ 验收标准引用                  ▼
        ▼                        实现 + 逐条举证
BENCHMARK.md（V1 的协议与记录规范）      │
        │                              ▼
        └──────────◄── 回写四份现状文档（规则见 §0.3）
```

**维护规则**：候选清单只增删、不排序；阶段一旦定下来，**它的验收标准写进对应文档**
（效果类进 `BENCHMARK.md`、能力类进 `CAPABILITIES.md`、架构类进 `ARCHITECTURE.md`），
本文件只保留指向与触发条件。
