# Avid — 需求规划（阶段 0 产出物 · 待确认）

> 状态：草案，等待签字确认。确认后本文档冻结为 v1，后续变更走"决策记录"追加。

## 1. 背景与问题

目标不是写一个聊天机器人，而是拥有一个**自己完全掌控的 agent 运行时（harness）**——
模型、工具、循环策略、记忆、权限、评测全部是自己的代码，可替换、可调试、可度量。

| 层次 | 问题 | 本项目的答案 |
|---|---|---|
| 能力层 | 想把某类任务交给 agent 自动完成 | 一个能自主多步调用工具的 loop |
| 工程层 | 用别人的框架 = 黑盒，prompt / 上下文 / 重试 / 权限都改不动 | 每一层都是自有代码，边界清晰、可替换 |
| 认知层 | 懂概念但没形成可运行整体；改动靠"感觉" | 有 trace、有评测集、有基线，改动可度量 |

## 2. 目标与成功标准

**项目级成功标准**：给定参考场景中的任务，agent 能稳定完成；并且

1. 能解释它每一步为什么这么做（trace 可回放）；
2. 能在 30 分钟内替换任一模块（模型 / 工具 / 记忆策略 / 上下文策略）而不改动其它部分；
3. 改动前后有可对比的评测数字。

**定位**：通用 harness 内核，先做内核，场景后接。

### 2.1 强制约束：参考场景（Reference Scenario）

选择"通用内核"路线的最大风险是失焦——做出一堆看起来完整、实际不可用的抽象。
因此强制：**内核的每个阶段都必须通过同一个参考场景验收**，不允许用"模块已完成"作为验收。

- **参考场景 R（v1 冻结）**：*读取本地文件 + 计算*。给定一个本地目录和一个问题
  （例："这些文件里哪个最大？把它们的总行数算出来"），agent 需自主选择工具、多步执行、给出正确答案。
- 特点：只读（无副作用）、正确性客观可判、无需网络、可构造评测集、恰好覆盖"工具调用 + 多步循环 + 上下文"。
- 后续场景（编码、检索、业务流）都作为 R 的**扩展**验证，不得绕过 R。

## 3. 使用者与使用方式

- 使用者：单人（作者本人），本地优先，单机运行。
- 形态：先 CLI；Web GUI 推迟到阶段 7，前端用 TypeScript。
- 外部依赖：仅 LLM API（OpenAI 兼容接口），无必须付费的其它服务。

## 4. 能力清单

### Must —— 没有它就不是 agent
1. 模型调用：OpenAI 兼容接口、流式、超时与重试、token 与成本统计
2. 工具调用：工具定义（schema）→ 模型发起 → 执行 → 结果回填
3. Agent 循环：多步"推理—行动—观察"，终止条件明确
4. 会话状态：消息结构规范化与序列化
5. 上下文组装：system + 历史 + 工具结果，在 token 预算内拼装
6. 可观测：每步原始输入输出落盘、可回放

### Should —— 决定它能否用于真实工作
7. 会话持久化与长期记忆
8. 权限 / 审批模型 + 工作区边界
9. 评测闭环（任务集、通过率、回归对比）
10. 子任务分解 / 子 agent 分派

### Later —— 明确推迟
11. 多 agent 编排、Web GUI、协议互操作（MCP 等）、插件生态、多用户

## 5. 非目标与解禁条件（Deferred, not Forbidden）

**性质说明**：以下条目是"当前主动不做"，用于防止在没想清楚时顺手开工，
**不是永久禁令**。每条都附解禁条件——条件满足即启动，不需要重新论证一遍。
真正的边界只有一条：项目的**架构定位**是编排层，不是模型层。

| 非目标 | 状态 | 解禁条件 |
|---|---|---|
| 训练 / 微调模型 | 架构外，基本不做 | 编排层与上下文策略均已优化到位、且被证明是瓶颈时，重新评估 |
| 多用户 SaaS 后端 | 暂缓 | 单人版稳定运行，且出现第二个真实使用者 |
| agent 自我修改自身代码 | 暂缓 | 阶段 4 评测基线与阶段 5 权限模型均已完成，且改动一律走人工审批 |
| 追求工具数量 / 铺开工具生态 | 暂缓 | 参考场景 R 通过后，按真实需要增量生长，不做"预埋" |
| 与商业产品功能对齐 | 不做对标 | 有具体价值的需求出现时按需求做，永不按竞品做 |
| 插件生态、协议互操作（MCP 等） | 暂缓 | 阶段 7，或出现"必须接某个外部系统"的真实需求 |

## 6. 约束

- **单人开发**：每个阶段都必须独立交付价值——任何阶段停下来，都留有一个能跑的东西
- **本地优先**：单机可跑，外部依赖只允许 LLM API
- **可读性 > 性能**：先要能看懂和改，不提前做并发 / 缓存优化
- **默认最小权限**：写文件、执行命令类工具从第一天起就带边界
- **技术栈固定**：Python 3.12 为内核语言；TypeScript 仅用于阶段 7 的前端；
  项目 / 环境管理优先用 `uv`，不可用时退回 `venv + pip`
- **配置与密钥**：一律走环境变量，密钥不入库
- **评测先行**（工作规则，非范围限制）：没有可对比的评测数字，不动 prompt 与循环策略；
  阶段 4 之前此类改动只能作为一次性实验，且必须在记录中标注"未经验证"
- **反过早抽象**（工作规则）：不为"以后可能需要"预留接口；
  第二次遇到同类需求时才抽公共层

## 7. 决策记录（Decision Log）

| ID | 决策 | 理由 | 代价 / 风险 |
|---|---|---|---|
| D-01 | 定位为通用 harness 内核，场景后接 | 最大化复用与掌控力 | 易失焦 → 由"参考场景"约束缓解 |
| D-02 | Python 3.12 写内核，TS 写后期前端 | 迭代快、生态成熟 | 后期存在双栈维护成本 |
| D-03 | 模型接入走 OpenAI 兼容 API | 兼容面最广、开箱可用 | 早期不做多 provider 抽象，避免过度设计 |
| D-04 | 形态先 CLI，Web GUI 推迟到阶段 7 | 内核优先，界面会拖慢早期 | 早期交互体验朴素 |
| D-05 | 阶段 4（评测）是分水岭 | 没有它，后续优化都是盲调 | 需要额外投入构造任务集 |
| D-06 | 非目标改为"暂缓 + 解禁条件"，不作永久禁令 | 过早封死方向会扼杀价值；但无约束的范围蔓延同样致命 | 需要自律：解禁必须满足条件，而非"想做就做" |
| D-07 | "评测先行"与"反过早抽象"定为工作规则而非范围限制 | 它们是做事方式，不是功能取舍 | 阶段 4 之前只能靠自觉遵守 |
