# 代码审查

## 顺序：先规格，后实现

1. **先确认这次改动要解决什么**。读 issue / 提交信息 / 相关测试。规格不清楚就先问，不要开始猜。
2. **再读实现**。带着"它是否解决了那个问题"去读，而不是从头到尾通读。
3. **最后读测试**。测试是规格的可执行版本；测试没覆盖的分支，就是最可能出问题的地方。

## 两条独立的审查轴

| 轴 | 问什么 | 常见发现 |
|---|---|---|
| **规格** | 需求都实现了吗？有没有顺手多加的东西？ | 漏掉边界情况；夹带了无关改动 |
| **标准** | 项目自己的约定遵守了吗？ | 命名不一致；错误处理方式与既有代码不同 |

两轴分开报告，不要混在一起——它们的修复责任人和优先级通常不同。

## 按严重度排序，而不是按文件顺序

- **必须改**：正确性问题、数据丢失风险、安全边界被绕过。
- **建议改**：可读性、重复代码、命名。
- **可以问**：你不确定的取舍——写成问题，不要写成命令。

每条意见必须包含：**位置 + 现象 + 为什么是问题 + 建议怎么改**。只说"这里不好"没有价值。

## 不要做的事

- 不要重写别人的实现来展示自己的写法。
- 不要在没有运行验证的情况下断言"这样更快/更安全"。
- 不要因为风格偏好把"建议"升级成"必须"。
- 不要漏掉测试：改动没有对应测试时，这一条单独列出来。
