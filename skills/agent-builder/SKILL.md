# 构建 agent 运行时

## 分层顺序（不要跳）

1. **模型调用层**：先用真实 key 打通一次调用，拿到 token 用量。没有这一步，后面全是 mock 出来的幻觉。
2. **循环骨架**：调用 → 追加 assistant 消息 → 判断有无工具调用 → 执行回填 → 下一轮。**先不注册任何工具**，确认"没有工具调用时正常退出"。
3. **第一个工具**：只加一个，验证完整的 tool-call 往返。工具分支在零工具时不可达，用假工具在测试里覆盖。
4. **工具集**：把定义与实现分开。定义集中放，实现按行为分组；加一个工具只应改两处。
5. **执行前校验**：危险操作先拦后审。硬拒绝（不可覆盖）→ 规则匹配 → 用户审批，顺序不能换。
6. **扩展点**：把策略从循环里搬进注册表 + 事件。循环只认事件名。
7. **规划能力**：带状态的 TODO 列表 + 长时间不更新时的提醒。
8. **并行派发**：子任务真正解耦时才用 subagent，否则串行更快。
9. **评测集**：到这一步之前，所有"变好了"都是感觉。

## 每层都要问的三个问题

- **没有它，会出什么具体的错？** 答不上来就是过早抽象。
- **验收靠什么命令？** 必须是可执行命令 + 实际输出，不接受"模块已完成"。
- **会不会让别的东西必须跟着改？** 会的话，先想清楚这个代价值不值。

## 最常见的三个失焦点

1. **先搭框架再打通调用**。结果框架的每一层都建立在没验证过的假设上。
2. **抽象早于第二次需求**。第一次遇到就抽公共层，抽出来的形状通常是错的。
3. **没有评测集就调 prompt**。改完不知道该跟什么比，只能凭印象。

## 工具定义的硬要求

- 每个参数都要写清类型与含义；数组参数必须声明元素结构。
- 失败返回文本、不要抛异常——循环要继续，模型才有机会自纠。
- 错误信息要**可操作**：说清是什么问题、以及下一步该怎么做。
- 拦截类错误要区分"永远不许"和"这次不行"，否则模型会反复重试同一条命令。
