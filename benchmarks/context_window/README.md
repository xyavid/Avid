# 上下文阈值随窗口（E2E）

``context.prepare`` 的 ③④ 判据原本是一个写死的 400_000 字符。它与模型的真实窗口无关，
于是同一个内核在两种情形下差一个量级：**中文**（1 字符 ≈ 1 token）还没到 40 万字符就已经
撞上 provider 的上下文超限，只剩 ⑤ 兜底；**1M 窗口**的模型则在用掉三分之一窗口时就被摘要。

现在阈值按**这次运行自己的实测读数**现算：

    阈值 = 窗口 × WINDOW_TRIGGER_RATIO(0.8) × 实测 chars/token −（系统提示 + 工具定义 字符）

`chars/token` 来自 `RunState.last_usage.prompt_tokens` 与 `RunState.prompt_parts`（发出那次
请求前记下的三块字符数）这一对读数，不是查表得来的语言系数——语言换了它跟着换。
缺任一项（没窗口、没读数）就**逐字**回落到 `CONTEXT_CHAR_LIMIT`。

## 怎么跑

    uv run --no-sync python benchmarks/context_window/run.py

不需要模型配置、不产生任何 API 调用：脚本真跑 `agent_loop` + 真的 `context.prepare` +
真的五步压缩 + 真的 hook 与落盘，只把**模型**换成一个"按窗口记账的标尺"——它按
「CJK 1 字符 ≈ 1 token、其余 4 字符 ≈ 1 token」数出这次请求的 token 数，超过窗口就像
provider 一样抛 `PromptTooLongError`。产物 `artifact.json` 可重跑（同一命令得到同一份文件
与同一组结论），退出码 1 表示有结论不成立。

## 四个臂

| 臂 | 窗口 | 内容 | 它证明什么 |
|---|---|---|---|
| `cjk_32k_fixed` | 32 768 | 中文 | 关掉派生（复现旧行为）：撞窗之前**零**压缩步，`③④` 连调都没被调到，全靠 provider 报错 |
| `cjk_32k_window` | 32 768 | 中文 | 同一份对话：0 次超窗，`③` 在发请求之前就压过 |
| `ascii_32k_window` | 32 768 | ASCII | 同窗口下派生阈值是中文臂的 3 倍以上：语言差异被实测换算率吸收 |
| `ascii_1m_first` | 1 000 000 | ASCII | 首轮还没有真实读数 → 逐字回落到 400 000（**有意保留**的那一段） |

## 实测（本仓库当前实现）

```
臂                        窗口   超限     最大占用         交给③④的阈值  压缩步序
cjk_32k_fixed         32768    1     1.00               -  reactive_compact
cjk_32k_window        32768    0     0.77     27463,28154  micro_compact,micro_compact
ascii_32k_window      32768    0     0.80   103674,103499  micro_compact,micro_compact
ascii_1m_first      1000000    0     0.14   400000,400000  compact_history
```

* 「最大占用」= 这次运行里最大的一次真实请求 token 数 ÷ 窗口。旧行为下是 **1.00**（已经撞上
  才被发现），新行为下是 0.77 / 0.80——阈值确实拦在了窗口之前。
* 两条派生臂的压缩事件 `detail` 里带着阈值来历（例：`阈值随窗口派生：27463 字符（窗口 32768
  × 0.8 × 实测 1.08 字符/token − 系统与工具 830 字符）`），消费事件流的一端据此能回答「为什么这一次会压」。

## 已知边界

**续接长会话的第一轮**没有本进程的实测读数，仍然回落到 400 000：如果那一条链已经超过窗口，
这一发会由 provider 报错、`⑤` 兜底压一次（多花一次调用、压得更重）。这是本轮有意不做的一段，
触发条件出现时的做法是把实测 `chars/token` 随用量快照落进会话值、续接时读回当种子。
